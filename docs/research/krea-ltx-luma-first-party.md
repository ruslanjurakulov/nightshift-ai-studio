## Why they are not for sale, and what was and was not read

**Krea.** Only the consumer Terms of Use (`krea.ai/terms`) were read; the copy says "Last updated: May 20, 2024" and may be a stale cache. They give each user "a worldwide, non-exclusive, non-sublicensable and non-transferable license to access, use ... content generated", bar "participate in the transfer or sale of ... the Services themselves", and say Krea "may allow you to commercialize certain Content generated from the Services" subject to restrictions "including pricing changes", which it "reserves the right to modify ... at any time". Nothing grants a right to resell. API or developer terms were NOT found at any URL tried (`/api-terms`, `/terms-of-service`). Gate `terms_review_required`: a person reads Krea's written terms, or asks sales (`sales@krea.ai`) for an Enterprise arrangement.

**LTX.** The LTX-2 API License Agreement (Last Updated May 12, 2026) 2.1(b) licenses the customer "to utilize the LTX Model in Customer's Service to be used by End Users" (1.19 counts a platform's downstream users), but 2.2(d) bars making it available "to any third party through a service bureau, resale or similar models". Whether a credits product is "resale" is the open question. 3.2 requires enforceable end-user agreements at least as protective of LTX (restrictions, the Acceptable Use Policy, disclaimers) and 3.3 makes the customer answer for End Users. 4.2: Customer Data (Input and Output) is the customer's and not used to train the LTX Model; 2.2(i): Output may not train competing models. The Acceptable Use Policy (March 30, 2026) adds that commercially used Output must not replicate a real likeness, brand or location unless cleared. Self-serve is prepaid credits; "Pay As You Go is available only to Enterprise Customers via Order Form". NOT read: the LTX-2 API Credit Terms and any order form.

**Luma.** Gate `written_consent_required`, as for Ray 3.2. The registry quote for Ray ("no product that substantially replicates Luma, and no output as a standalone service, without Luma's prior written consent") was NOT re-read. The general Terms of Service (Last updated May 14, 2026, `lumalabs.ai/legal/tos`) 3.4(b) bar service-bureau use but say the restriction "does not prohibit API Customers from using the APIs to connect the Services with Customer's own applications and services or to provide API Users with access to the Services", and defer API customers to "API Terms of Use", which were NOT found at any URL tried. So the general ToS looks more permissive than the carried-over note: that is a reason to read the API terms, not to clear the gate. The ToS also says the customer owns Output (section 10), that Output which identifies or resembles a person must be publicly identified as AI generated (section 4), and that the customer answers for its API Users.

No age rule for the customer was found for Krea beyond "legal age to contract or parent's permission (under 13 barred)", and none for LTX or Luma in the text read. Sign-up and payment from Uzbekistan were verified for none of them.

## What the adapters do

- **Krea** (`docs.krea.ai`, read 2026-10-25: Krea 3 overview, job lifecycle, API keys and billing). `POST /generate/image/krea/krea-3` answers `job_id`; `GET /jobs/{id}` answers `status` and `result.urls[0]` (a failed job: `result.error`). `thinking_mode` is always sent `fast`: `high` is +$0.02 and `ultra` +$0.20 per image, so neither is offered. `resolution` is always sent explicitly, `1K` unless the job names a size. **2K ($0.06) is supported by the adapter and told in the price note but not offered by the registry**: the creative bridge passes no image size and the quote prices the base unit only (the same blind spot the Gemini image entries already have), so a 2K job would be sold at the 1K figure. **Bounding boxes (`regions`) are documented but UNVERIFIED here and never sent**; there is no request path for them. `regional_edit: true` is sent only by `krea-3-regional`, whose vendor model `krea-3:regional` is our name (the suffix is stripped; Krea has one endpoint and no model field). Reference pictures add to the price (+$0.02 per 1K reference, +$0.07 per 2K reference; the docs do not say how a picture is classed), so an edit takes exactly one picture and the registry price does not cover that surcharge. Not sent: `width`/`height`, `priority`, `seed`, `loras`/`style_urls` (a 422 on Krea 3), the zero-data-retention header.
- **LTX** (`docs.ltx.io`, read 2026-10-25: async jobs, text- and image-to-video references, job status, models, pricing, errors, rate limits, input formats). `POST /v2/text-to-video` or `/v2/image-to-video` answers 202 `id`; `GET /v2/{endpoint}/{id}` answers `status` (pending, processing, completed, failed), `result.video_url` and `error {type, message}`. The endpoint is part of the stored task id (`text-to-video:<id>`). `duration` and `resolution` are required and sent as given; automatic duration (`null`) is never sent (the vendor holds credits for the longest clip). `fps` is always `24`. Fast takes 12-20 s only at 720p/1080p; Pro stops at 10 s; 2.3 is 16:9 and 9:16 only. Not wired: audio-to-video, retake, extend, HDR, reframe, a last frame, camera motion. The default concurrency limit is 2; the registry says 1.
- **Luma** (`docs.agents.lumalabs.ai`, read 2026-10-25: image generation, models, pricing, error handling). The envelope is the Ray adapter's: `POST /v1/generations` (`type: "image"`, `output_format: "png"`), `GET /v1/generations/{id}`. Every output is 2K. Edit, `image_ref` (+$0.003 each) and `web_search` are not wired.
- Every submit whose answer never came back (timeout, dropped connection, 5xx, an unreadable 2xx) raises with `not_accepted` False and a message that starts with `UNCONFIRMED SPEND`; the worker neither retries it nor moves it to another model. Every failure after the vendor said the work was done (a bad link, a refused download, a bad file) starts with `SPEND MAY HAVE OCCURRED`. None of the vendors' "failed jobs are not billed / refunded" statements is repeated as fact; Krea's and Luma's are quoted in the notes as vendor claims.
- **Result hosts.** Krea: `krea.ai` (the docs show `krea.ai/generations/...` and `gen.krea.ai`; a real result host was not seen). LTX: only `storage.googleapis.com`, the one host the docs show, which is shared by every Google Cloud customer and cannot be narrowed from the docs. **Luma: none.** The docs show a placeholder (`storage.example.com`) and no real host, so `RESULT_HOSTS` is empty and every link is refused (fail closed): the first real probe fails with `SPEND MAY HAVE OCCURRED ... 'the host it saw'`, and a person puts that host in `modules/capabilities/luma.py` once it is checked to be Luma's. Until then `luma-uni-1` cannot pass a probe.

## To enable one (owner)

1. Settle the terms: Krea (read written terms or ask sales), LTX (is a credits product "resale"? ask Lightricks), Luma (read the API Terms of Use or get written consent).
2. Set the repository secret (`KREA_API_KEY`, `LTX_API_KEY`; Luma's key is already `LUMA_AGENTS_API_KEY`), never in chat; set a spend cap.
3. `python tools/probe_models.py --dry-run --model <id>`, then the real probe by name: about $0.03 (`krea-3`), $0.05-0.10 (`krea-3-regional`: base plus the reference surcharge), $0.18-$0.72 (an LTX 6 s clip at 720p), $0.04 / $0.10 (Luma). Read the result host off a failed Luma probe.
4. Re-check the prices, set `confirmed: true`, add the `credit_prices` rows, clear `terms_gate` in a reviewed change. For Krea, decide how a size is priced before offering 2K.
